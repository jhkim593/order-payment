## 0002. 취소 식별자를 주문이 발급하고 결과까지 따라다니게 한다

**상태:** 승인 · 2026-10-04

### 맥락

부분 취소에서는 한 주문에 취소가 N건 생긴다. 지금 결제가 돌려주는 이벤트 페이로드는 `(paymentId, orderId)`뿐이라 **어느 취소 건의 결과인지 구분할 수 없다.** 2건을 보냈는데 성공 1건이 돌아오면 어느 쪽인지 모른다.

### 결정

주문이 `cancellationId`(Snowflake)를 발급하고, 그 값이 전 구간을 따라다닌다.

```
order_cancellation.cancellation_id
  → ORDER_CANCEL 페이로드
  → payment_cancellation PK
  → 결제사 멱등키
  → 결과 이벤트 페이로드
```

이벤트 페이로드 변경:

| 페이로드 | 추가 |
|---|---|
| `OrderCancelEventPayload` | `cancellationId`, `amount` |
| `PaymentCancelSucceededEventPayload` | `cancellationId` |
| `PaymentCancelFailedEventPayload` | `cancellationId` |

### 이유

아웃박스의 `eventId`를 쓰는 안도 검토했다. 전송 중복(재전송, DLT 재투입, 리스너 재시도)은 막아주지만, 주문이 취소 건을 추적할 식별자를 어차피 따로 만들어야 하므로 id가 둘이 된다. 하나로 합치는 편이 단순하고, 업무 식별자라 결과 이벤트에 실어 되돌려 보낼 수 있다.

`amount`를 이벤트에 싣는 것은 결제가 주문의 상품 구조를 볼 수 없기 때문이다. 금액 계산은 주문의 책임이고 결제는 숫자만 받는다.

### 결과

중복 방지 책임이 계층별로 갈린다.

| 책임 | 어디서 | 무엇으로 |
|---|---|---|
| 요청 중복 (같은 상품 두 번 취소) | 주문 | 취소 수량 가드 |
| 전송 중복 (같은 이벤트 두 번 수신) | 결제 | `cancellation_id` PK 충돌 |
| 호출 중복 (같은 요청 결제사에 두 번) | 결제사 | 멱등키 |

## 0001. 취소를 별도 테이블로 분리하고 상품 단위로 기록한다

**상태:** 승인 · 2026-10-04

### 맥락

부분 취소를 하려면 "어떤 상품을 몇 개 취소했는지"와 "그 취소가 어디까지 진행됐는지"를 알아야 한다. `orders.status` 한 칸으로는 "일부만 취소됨"을 표현할 수 없고, 취소가 진행 중인지도 둘 곳이 없다.

### 결정

테이블 둘로 나눈다.

- `order_cancellation` — 취소 건. 금액 합계, 상태, 시도 정보
- `order_cancellation_product` — 그 건에 포함된 상품과 수량

`order_product`에 `cancelled_quantity`(누적)를 더한다. 가드는 `cancelled_quantity + 요청수량 <= quantity`다.

`orders.status`에서 취소 관련 값을 뺀다. 주문이 전부 취소됐는지는 취소 건들의 금액 합계로 판단한다.

### 이유

취소 1건이 상품 여러 개를 묶을 수 있어야 자식 테이블이 필요하다. **묶는 이유는 결제사 호출을 한 번으로 만들기 위해서다.** 상품별로 쪼개면 3개 취소에 호출 3번이고, 그중 하나가 타임아웃 나면 "1건 성공, 1건 실패, 1건 미확정"인 상태를 사람이 풀어야 한다.

누적 컬럼은 취소 **요청 시점에** 올린다. 처리 중인 수량까지 포함해야 동시 요청이 한도를 넘지 않는다. 실패로 확정되면 되돌리고, 미확정이면 되돌리지 않는다.

### 대안

취소 1건 = 상품 1개로 제한하면 테이블 하나로 끝난다. 묶음 취소 UI가 요구사항에 있어 택하지 않았다. 상품 목록을 JSON 컬럼에 넣는 안은 수량 가드를 SQL로 집계할 수 없고 중복 방지 제약도 걸 수 없어 제외했다.
