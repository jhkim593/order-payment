## 0004. 재고 변경 시 상품을 ID 순으로 잠그고, 잠근 뒤 최신 값으로 다시 읽는다

**상태:** 승인 · 2026-10-07

### 맥락

재고는 도메인 메서드(`decreaseStock`, `increaseStock`)로 바꾸고 더티 체킹으로 반영한다. 더티 체킹은 "얼마를 더했는지"가 아니라 "최종 값"을 `UPDATE`하므로, 계산의 출발점이 최신 값이어야 한다.

결제 실패·취소 성공 경로는 주문을 `find`(상품까지 fetch join)로 먼저 읽는다. 이때 상품이 **락 없이** 영속성 컨텍스트에 올라온다. 이후 `SELECT ... FOR UPDATE`로 다시 조회해도 DB 행에 락만 걸리고, Hibernate는 1차 캐시에 있던 기존 객체를 그대로 돌려준다. 그 사이 다른 트랜잭션이 바꾼 재고를 덮어쓰게 된다.

```
T1: find(주문) → 상품 A stock=10 (락 없음)
T2: A 10 → 8, 커밋
T1: FOR UPDATE → 락은 걸리지만 객체는 10 그대로 → +3 → UPDATE stock=13 (정답 11)
```

### 결정

- `ProductRepository.findAllForUpdate(ids)`는 `ORDER BY product_id ... FOR UPDATE` 한 쿼리로 잠근다.
- 잠근 뒤 각 상품을 `EntityManager.refresh`로 다시 읽는다. 락을 잡은 상태라 읽은 값은 커밋 전까지 바뀌지 않는다.
- `refresh`는 어댑터(`ProductDBRepository`) 안에만 둔다. 서비스는 `EntityManager`를 모른다.

### 이유

호출하는 쪽이 주문·상품을 어떻게 읽었든 재고 변경이 항상 최신 값에서 출발한다. `find`의 fetch join(조회 용도)을 바꾸지 않아도 되고, "재고를 먼저 바꾸고 주문은 나중에 읽는다" 같은 호출 순서 전제가 생기지 않는다.

ID 순 정렬은 데드락 방지다. 주문 1이 A→B, 주문 2가 B→A 순으로 잠그면 서로를 기다린다. 모든 트랜잭션이 같은 순서로 잠그면 늦게 온 쪽이 첫 행에서 기다릴 뿐이다.

### 대안

- **락 먼저 (호출 순서로 해결)** — 주문의 상품 ID·수량을 프로젝션(스칼라) 조회로 먼저 꺼내고, 재고를 잠가 바꾼 뒤 주문을 읽는다. 프로젝션은 영속성 컨텍스트에 올라가지 않아 락 조회가 상품을 처음 읽는다. 쿼리는 적지만 순서가 TM 코드에만 있어, 누가 순서를 바꾸면 조용히 다시 깨진다.
- **상품 없이 주문 조회 (`findWithoutProduct`)** — 상품을 프록시로 남겨 락 조회가 처음 읽게 한다. 같은 원리이고, 재고용 조회 메서드가 따로 생긴다. 다른 곳에서 상품을 먼저 로딩하면 같은 문제가 재발한다.
- **`find`에서 상품 fetch join 제거** — 읽기 용도의 조회를 쓰기 경로 때문에 바꾸게 된다.
- **`FOR UPDATE OF p`로 주문 조회 시 상품만 잠금** — 한 쿼리로 끝나지만 JPA 표준으로는 별칭 지정이 안 돼 네이티브 쿼리나 Hibernate 전용 API가 필요하다. `DISTINCT`·`LEFT JOIN`과 함께 쓸 수 없는 Postgres 제약도 있다. 주문 리포지토리가 상품 락까지 맡게 되어 상품 도메인 경계(`ProductUpdater`)와도 어긋난다.
- **`UPDATE product SET stock = stock + ?`** — 메모리 값을 쓰지 않아 문제 자체가 없지만, 재고 규칙이 SQL로 빠져 도메인 메서드와 갈린다.
- **`EntityManager.detach`/`clear`** — 주문이 들고 있는 상품 참조까지 끊겨 더 복잡하다.

### 결과

재고를 바꿀 때 상품 수만큼 `SELECT`가 한 번씩 더 나간다. 한 주문의 상품 수가 적어 감수한다. `refresh`는 그 엔티티의 아직 반영되지 않은 변경을 버리므로, 잠그기 전에 같은 상품을 메모리에서 수정하는 코드를 두지 않는다.

## 0003. 재고는 주문 생성 시 차감하고 결제 실패·취소 성공 시 복원한다

**상태:** 승인 · 2026-10-06

### 맥락

상품마다 재고 수량을 관리한다. 주문은 생성 → 결제 → 결과 수신 순으로 진행되므로, 어느 시점에 재고를 줄일지 정해야 한다.

### 결정

- 주문 생성 시 재고를 차감한다. 주문한 상품 중 하나라도 모자라면 주문 전체를 거절한다.
- 결제 실패가 확정되면 차감한 재고를 복원한다.
- 취소 성공이 확정되면 취소한 수량만큼 복원한다. 미확정 취소는 복원하지 않는다 — 실제로는 환불이 나갔을 수 있다.

### 이유

결제가 진행되는 동안 재고를 점유해야 같은 재고를 두 주문이 동시에 가져가지 않는다.

### 대안

**결제 성공 시 차감** — 결제 중에 재고를 잡아두지 않아, 결제는 성공했는데 재고가 없는 주문이 생길 수 있다. 그러면 자동 환불 경로가 따로 필요해서 택하지 않았다.

### 결과

결제 실패나 취소 성공이 확정되지 않으면 재고가 돌아오지 않는다.

## 0002. 취소 식별자를 주문이 발급하고 결과까지 따라다니게 한다

**상태:** 승인 · 2026-10-04

### 맥락

부분 취소에서는 한 주문에 취소가 N건 생긴다. 지금 결제가 돌려주는 이벤트 페이로드는 `(paymentId, orderId)`뿐이라 **어느 취소 건의 결과인지 구분할 수 없다.** 2건을 보냈는데 성공 1건이 돌아오면 어느 쪽인지 모른다.

### 결정

주문이 `cancellationId`(Snowflake)를 발급하고, 그 값이 전 구간을 따라다닌다.

```
order_cancellation.cancellation_id
  → ORDER_CANCEL 페이로드
  → payment_cancellation PK
  → 결제사 멱등키
  → 결과 이벤트 페이로드
```

이벤트 페이로드 변경:

| 페이로드 | 추가 |
|---|---|
| `OrderCancelEventPayload` | `cancellationId`, `amount` |
| `PaymentCancelSucceededEventPayload` | `cancellationId` |
| `PaymentCancelFailedEventPayload` | `cancellationId` |

### 이유

아웃박스의 `eventId`를 쓰는 안도 검토했다. 전송 중복(재전송, DLT 재투입, 리스너 재시도)은 막아주지만, 주문이 취소 건을 추적할 식별자를 어차피 따로 만들어야 하므로 id가 둘이 된다. 하나로 합치는 편이 단순하고, 업무 식별자라 결과 이벤트에 실어 되돌려 보낼 수 있다.

`amount`를 이벤트에 싣는 것은 결제가 주문의 상품 구조를 볼 수 없기 때문이다. 금액 계산은 주문의 책임이고 결제는 숫자만 받는다.

### 결과

중복 방지 책임이 계층별로 갈린다.

| 책임 | 어디서 | 무엇으로 |
|---|---|---|
| 요청 중복 (같은 상품 두 번 취소) | 주문 | 취소 수량 가드 |
| 전송 중복 (같은 이벤트 두 번 수신) | 결제 | `cancellation_id` PK 충돌 |
| 호출 중복 (같은 요청 결제사에 두 번) | 결제사 | 멱등키 |

## 0001. 취소를 별도 테이블로 분리하고 상품 단위로 기록한다

**상태:** 승인 · 2026-10-04

### 맥락

부분 취소를 하려면 "어떤 상품을 몇 개 취소했는지"와 "그 취소가 어디까지 진행됐는지"를 알아야 한다. `orders.status` 한 칸으로는 "일부만 취소됨"을 표현할 수 없고, 취소가 진행 중인지도 둘 곳이 없다.

### 결정

테이블 둘로 나눈다.

- `order_cancellation` — 취소 건. 금액 합계, 상태, 시도 정보
- `order_cancellation_product` — 그 건에 포함된 상품과 수량

`order_product`에 `cancelled_quantity`(누적)를 더한다. 가드는 `cancelled_quantity + 요청수량 <= quantity`다.

`orders.status`에서 취소 관련 값을 뺀다. 주문이 전부 취소됐는지는 취소 건들의 금액 합계로 판단한다.

### 이유

취소 1건이 상품 여러 개를 묶을 수 있어야 자식 테이블이 필요하다. **묶는 이유는 결제사 호출을 한 번으로 만들기 위해서다.** 상품별로 쪼개면 3개 취소에 호출 3번이고, 그중 하나가 타임아웃 나면 "1건 성공, 1건 실패, 1건 미확정"인 상태를 사람이 풀어야 한다.

누적 컬럼은 취소 **요청 시점에** 올린다. 처리 중인 수량까지 포함해야 동시 요청이 한도를 넘지 않는다. 실패로 확정되면 되돌리고, 미확정이면 되돌리지 않는다.

### 대안

취소 1건 = 상품 1개로 제한하면 테이블 하나로 끝난다. 묶음 취소 UI가 요구사항에 있어 택하지 않았다. 상품 목록을 JSON 컬럼에 넣는 안은 수량 가드를 SQL로 집계할 수 없고 중복 방지 제약도 걸 수 없어 제외했다.
