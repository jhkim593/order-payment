# 0005. 주문의 결제 결과는 응답과 이벤트로 확정하고, 응답을 못 받은 주문만 결제 건 유무를 확인한다

## 2026-10-13 (적용 중)

### 배경

- 주문은 결제를 HTTP로 호출한다. 호출이 타임아웃·연결 끊김·5xx로 끝나면 결제가 됐는지 알 수 없다. 요청이 결제까지 못 갔을 수도, 결제는 됐는데 응답만 잃었을 수도 있다
- 이를 실패로 확정하면 돈은 빠져나갔는데 주문은 실패하고 재고가 복원될 수 있다
- 호출이 끝난 뒤 확정된 결과를 주문이 받을 경로가 필요하다

### 결정

- 결제 응답: 200 → `SUCCEEDED`, 202 → `PAYMENT_REQUESTED`, 4xx(`PAYMENT_ALREADY_EXISTS` 제외) → `FAILED` + 재고 복원, 그 외(500·타임아웃·연결 실패) → `PENDING` 유지. 결제 에러 코드는 보지 않는다
- 결과를 모르면(`PENDING`·`PAYMENT_REQUESTED`) 에러 대신 202로 응답해, 클라이언트에게 처리 중임을 알린다. 응답 코드는 결제 응답 기준으로 정하고, 이후 확정분은 주문 서비스 안에서만 반영한다
- 응답 뒤의 확정은 결제 결과 이벤트로 반영한다. 결제 건이 있으면 이벤트가 반드시 온다
- 결제 요청이 결제까지 못 갔다면 결제 건이 없어 이벤트도 오지 않는다. 이 주문을 정리하려고 확인 스케줄러를 둔다
- 확인 스케줄러는 결제 건 유무만 본다. 생성 2분 지난 `PENDING`을 한 번 조회해 없으면 `FAILED` + 재고 복원, 있으면 `PAYMENT_REQUESTED`로 두고 결과는 이벤트에 맡긴다. 2분은 결제 호출 타임아웃(80초)보다 길어 응답 처리와 겹치지 않는다
- 상태 변경은 조건부 UPDATE(`WHERE status IN updatableFrom()`). 0행이면 이미 반영된 것이라 넘겨, 응답·이벤트·스케줄러가 겹쳐도 재고는 한 번만 복원된다. UPDATE는 트랜잭션에서 주문을 처음 건드리는 곳에 둔다

### 트레이드오프

- 얻는 것: 결과를 모르는 주문을 실패로 확정하지 않고, 확인 조회는 응답을 못 받은 주문만 한 번으로 끝난다
- 감수하는 것: 상태 전이 조건이 SQL에 들어간다
- 감수하는 것: 클라이언트는 202를 받은 주문의 최종 결과를 알 수 없다
- 감수하는 것: 결제가 `UNKNOWN`이거나 이벤트가 DLT로 빠지면 주문이 확정되지 않고 남는다
- 감수하는 것: 결제 요청이 2분 넘게 늦게 도착하면, 실패 처리한 주문에 결제가 생길 수 있다
