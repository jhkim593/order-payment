# 0006. 주문 조회는 주문 DB만으로 응답하고, 결제 정보는 화면이 결제 API로 따로 조회한다

## 2026-10-21 (적용 중)

### 배경

- 주문 조회 화면에는 주문·상품 정보와 결제 정보가 필요한데, 결제 정보는 결제 서비스에 있다
- 주문 조회가 결제 서비스를 호출하면 결제 장애·지연이 주문 조회로 번진다
- 조회 전용 서비스(CQRS)를 검토했으나, 목록은 주문 데이터만으로 충분하고 다른 서비스 데이터가 필요한 건 결제 상세 하나뿐이다

### 결정

- 주문 조회는 주문 DB만 읽는다. 결제 정보는 응답에 넣지 않고, 화면이 기존 결제 조회 API(`GET /api/v1/payment/order/{orderId}`)로 따로 가져온다
- 목록은 요약(주문 일시·상태·총 금액·대표 상품·나머지 상품 수), 상세는 상품별 수량과 취소 내역
- 목록은 커서 페이징(무한 스크롤). 커서는 마지막 항목의 `order_id`, 20건씩. `order_id`가 생성 순서대로 증가하므로 `order_id` 역순을 최신순으로 쓴다. 페이지 번호 방식은 새 주문이 생기면 결과가 밀린다. 인덱스 `(user_id, order_id DESC)`
- 목록은 `userId` 쿼리 파라미터로 사용자를 받는다. 상세는 주문 번호만으로 조회하고 본인 확인은 하지 않는다. 사용자 인증이 아직 없어 확인할 근거가 없다
- CQRS는 도입하지 않는다. 지금은 복제·최종 일관성·순서 처리 비용만 생긴다. 목록에 여러 서비스 데이터가 필요해지거나, 조회 부하가 쓰기에 영향을 주거나, 검색·집계가 필요해지면 도입한다
- 캐시는 두지 않는다. 상세는 PK 조회라 충분히 빠르다

### 트레이드오프

- 얻는 것: 새 서비스·이벤트 없이 조회를 제공하고, 결제 장애가 주문 조회에 번지지 않는다
- 감수하는 것: 화면이 주문 상세와 결제 상세를 두 번 호출한다
- 감수하는 것: 조회가 쓰기 DB를 함께 쓴다. 부하가 측정되면 읽기 복제본으로 보낸다
- 감수하는 것: 인증이 붙기 전까지 주문 번호나 `userId`만 알면 다른 사람의 주문을 볼 수 있다
