# 0005. 주문 생성: 재고는 생성 시 차감하고, 결제 결과는 응답과 이벤트로 확정한다

## 2026-10-27 (적용 중)

### 배경

- 결제 중 재고를 점유하지 않으면 같은 재고를 두 주문이 가져갈 수 있다
- 결제 호출이 타임아웃·연결 끊김·5xx로 끝나면 결제 여부를 알 수 없다. 실패로 확정하면 돈은 빠졌는데 재고가 복원될 수 있다
- 결과가 응답·이벤트·확인 스케줄러로 겹쳐 올 수 있다
- 인기 상품에 주문이 몰리면 모두 같은 상품 행에서 줄을 선다. 기존 방식은 트랜잭션 맨 앞에서 `FOR UPDATE`로 잠그고 주문 INSERT·커밋까지 쥐고 있어, 잠금 시간이 곧 처리량 상한이었다

### 결정

- 재고는 주문 생성 시 차감한다. 하나라도 모자라면 주문 전체를 거절한다
- 결제 실패가 확정되면 전량, 취소 성공이 확정되면 취소 수량만큼 복원한다. 미확정은 복원하지 않는다
- 재고 변경은 조건부 UPDATE(`stock = stock - :qty WHERE stock >= :qty`)로 한다. 0행이면 품절이다. 메모리에서 재고를 바꾸지 않으므로 `FOR UPDATE`·`refresh`가 필요 없다
- 주문 생성에서 재고 차감은 주문 INSERT 뒤, 트랜잭션 맨 끝에 둔다. 행 잠금이 UPDATE부터 커밋까지만 잡힌다. 상품 존재 확인은 앞에서 잠금 없이 조회한다
- 여러 상품은 `product_id` 순서로 UPDATE해 데드락을 막는다
- 결제 응답: 200 → `SUCCEEDED`, 202 → `PAYMENT_REQUESTED`, 4xx(`PAYMENT_ALREADY_EXISTS` 제외) → `FAILED` + 재고 복원, 그 외 → `PENDING` 유지
- 결과를 모르면(`PENDING`·`PAYMENT_REQUESTED`) 202로 응답한다. 이후 확정은 결제 결과 이벤트로 반영한다
- 결제까지 못 간 주문은 확인 스케줄러가 정리한다. 2분 지난 `PENDING`을 한 번 조회해 결제 건이 없으면 `FAILED` + 재고 복원, 있으면 `PAYMENT_REQUESTED`. 2분은 결제 호출 타임아웃(80초)보다 길다
- 상태 변경은 조건부 UPDATE(`WHERE status IN updatableFrom()`)를 트랜잭션 맨 앞에 둔다. 0행이면 이미 반영된 것이라 넘겨 재고는 한 번만 복원된다

### 트레이드오프

- 얻는 것: 결제는 됐는데 재고가 없는 주문이 생기지 않고, 결과를 모르는 주문을 실패로 확정하지 않는다
- 얻는 것: 상품 행 잠금 시간이 UPDATE 한 줄과 커밋으로 줄어 같은 상품 동시 주문 처리량이 늘어난다
- 감수하는 것: 결제 실패·취소 성공이 확정되지 않으면(결제 `UNKNOWN`, 이벤트 DLT) 재고가 돌아오지 않는다
- 감수하는 것: 재고·상태 전이 조건이 SQL에 들어가고, 영속성 컨텍스트의 상품 재고 값은 갱신되지 않는다
- 감수하는 것: 클라이언트는 202를 받은 주문의 최종 결과를 알 수 없다
- 감수하는 것: 결제 요청이 2분 넘게 늦게 도착하면, 실패 처리한 주문에 결제가 생길 수 있다

- 감수하는 것: 재고 변경 시 상품 수만큼 `SELECT`가 더 나가고, 잠그기 전에 같은 상품을 메모리에서 수정하면 안 된다
