# 0001. 주문 취소는 상품 단위 취소 건으로 기록하고, 결과는 취소 건마다 한 번만 반영한다

## 2026-10-14 (적용 중)

### 배경

- 부분 취소를 하려면 어떤 상품을 몇 개 취소했는지, 그 취소가 어디까지 진행됐는지 알아야 한다
- 한 주문에 취소가 N건 생기는데, 결제 이벤트 페이로드 `(paymentId, orderId)`로는 어느 취소 건의 결과인지 구분할 수 없다
- 결과 이벤트는 중복 전달될 수 있다(재시도 토픽·리밸런스). 동시에 처리되면 재고가 두 번 복원된다

### 결정

- `order_cancellation`(취소 건) + `order_product_cancellation`(상품과 수량). 취소 1건이 여러 상품을 묶는다. 결제사 호출이 한 번이라 부분 성공이 없다
- `order_product.quantity`는 남은 수량. 취소 성공 시에만 줄여 실패 때 되돌릴 것이 없다. `orders.status`에는 취소 값을 두지 않는다
- 주문이 `cancellationId`(Snowflake)를 발급해 결과 이벤트까지 싣는다. 금액도 주문이 계산해 페이로드에 싣는다
- 접수: 진행 중(`PENDING`) 취소가 있거나 요청 수량이 남은 수량을 넘으면 요청 전체를 거절한다. 동시 요청은 부분 유니크 인덱스 `(order_id) WHERE status = 'PENDING'`가 막고, 이 위반은 변환하지 않는다
- 결과: 조건부 UPDATE(`WHERE status IN updatableFrom()`)를 트랜잭션 맨 앞에 둔다. 0행이면 이미 반영된 것이라 넘긴다. 결과 중복은 취소 건 단위로 막아야 지난 취소 건의 중복 이벤트도 걸러진다
- 성공은 남은 수량 차감 + 재고 복원, 실패는 상태만 `FAILED`. 미확정은 `PENDING`으로 남아 환불이 나갔을 수 있는 수량의 재취소를 막는다

### 트레이드오프

- 얻는 것: 취소 건 하나의 id로 요청부터 결과까지 추적되고, 결과가 몇 번 와도 재고는 한 번만 복원된다
- 감수하는 것: 원래 주문 수량은 남은 수량 + 성공한 취소 수량으로 계산해야 한다
- 감수하는 것: 동시 접수에서 밀린 요청은 409가 아니라 500을 받는다
- 감수하는 것: 결과 상태 전이 조건이 SQL에 들어간다
