# 0007. 재고 이력: 재고 변경과 같은 트랜잭션에 덧붙이는 이력 테이블을 둔다

## 2026-10-27 (적용 중)

### 배경

- 재고는 `product.stock` 숫자만 바뀌어, 언제 왜 바뀌었는지 추적하거나 숫자가 맞는지 검증할 방법이 없다
- 재고를 채우는 기능이 없어 SQL로 직접 바꾸고 있고, 그 기록도 남지 않는다

### 결정

- `stock_history`에 변경마다 한 행을 INSERT한다. 현재 재고는 계속 `product.stock`이 기준이고, 이력은 덧붙이기만 한다. 이력 합계로 재고를 계산하지 않는다
- 이력 INSERT는 재고 UPDATE와 같은 트랜잭션에서, UPDATE보다 앞에 둔다. 상품 행 잠금 시간이 늘지 않고(0005), 품절이면 트랜잭션 전체가 롤백되어 이력도 남지 않는다
- 사유는 `ORDERED`(−), `ORDER_FAILED`(+), `CANCELLED`(+), `RESTOCKED`(+). 결제 실패가 응답·이벤트·확인 스케줄러 중 어디로 왔는지는 사유로 나누지 않는다. 주문 실패라는 사실만 남기고 상세 원인은 주문 쪽에서 본다
- 참조는 하나의 `ref_id`에 섞지 않고 `order_id`·`cancellation_id` 컬럼으로 나눠 FK를 건다
  - `ORDERED`·`ORDER_FAILED`: `order_id`만
  - `CANCELLED`: 둘 다. 부분 취소가 여러 번일 수 있어 취소 건까지 구분한다
  - `RESTOCKED`: 둘 다 없음
- 재고 변경은 주문 객체가 아니라 사유와 참조 ID(`StockChange`)만 받는다. 상품 쪽 코드는 주문 코드에 의존하지 않고, 받은 ID를 그대로 기록한다
- 입고는 `POST /api/v1/products/{productId}/restock`으로 받는다
- 마이그레이션에서 기존 재고를 `RESTOCKED` 이력으로 한 번 넣어, 처음부터 이력 합계와 현재 재고가 같게 한다

### 트레이드오프

- 얻는 것: 장시간 운영 후에도 상품별 이력 합계와 현재 재고를 비교해 정합성을 검증할 수 있다
- 감수하는 것: 재고 변경마다 상품 수만큼 INSERT가 늘고, 이력 테이블은 계속 커진다
