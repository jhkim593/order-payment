# 0004. 결제 취소: 진행 중인 취소는 하나만 두고, 결과는 결제사의 누적 취소 금액으로 확정한다

## 2026-10-14 (적용 중)

### 배경

- 부분 취소를 도입하면 한 결제에 취소가 N건 생기는데, `payment` 한 행이 취소 한 건을 겸해 1:N으로 늘어날 수 없다
- 취소는 결제사가 `cancellation.id`를 발급하고 우리 식별자를 넣을 필드가 없다. 응답이 유실되면 어느 취소가 반영됐는지 알 수 없고, 같은 금액 취소가 2건이면 금액으로도 구분되지 않는다
- 부분 취소 후 결제사 상태는 `PARTIAL_CANCELLED`라 상태로 판정할 수 없고, 취소 응답이 `REQUESTED`(PG사 처리 중)일 수 있다

### 결정

1. **중복 수신**: 같은 `cancellationId`가 다시 오면 결제사를 부르지 않고 넘긴다
2. **취소 건 생성**: `payment_cancellation` 테이블에 취소 건을 기록한다. 취소 건마다 금액·상태·확인 횟수를 갖고, 취소된 금액은 `Payment`가 취소 목록에서 계산한다(실패 건 제외). 한 결제의 취소 여러 건이 서로 다른 상태로 진행되는 것이 정상인 구조가 된다
   - 가드 통과 → `PENDING`으로 기록하고 결제사를 호출한다
   - 결제 미완료, 남은 금액 초과, 다른 취소 진행 중(`PENDING`·`UNKNOWN`) → 결제사를 부르지 않고 `FAILED`로 기록해 취소 실패 이벤트를 발행한다. 기록이 있어야 결과가 전달되고 재수신이 걸러진다
   - 진행 중인 취소를 하나로 제한하면 미확정 건이 항상 하나라 식별자 매핑이 필요 없고, 미확정 취소 위에 초과 환불하는 경우도 막힌다. 같은 가드를 주문에도 둔다
3. **결제사 호출**: `currentCancellableAmount` = 직전 잔액, 멱등키 = `cancellationId`. 잔액 조건은 기한 없는 이중 환불 방어(멱등키는 3시간 뒤 만료)
4. **응답 판정**:
   - `SUCCEEDED` → 성공
   - `FAILED`·4xx → 실패
   - `REQUESTED`·5xx·타임아웃 → `PENDING` 유지. `REQUESTED`를 성공으로 보면 PG사가 나중에 거절했을 때 잘못 통지한다
5. **확인**: 결제사 `amount.cancelled`가 예상 누적 취소(성공 합계 + 확인 중인 건)와 같으면 성공, 아니면 다음 확인을 기다린다. 누적 금액은 처리 중과 거절을 구분하지 못해 확인에서는 실패를 확정하지 않는다. 점유·간격·횟수는 결제(0001)와 같다
6. **한도 소진·수동 확정**: 결제(0001)와 같다. 상태는 `CANCEL_UNKNOWN`

### 트레이드오프

- 얻는 것: 결제사 취소 내역을 우리 건과 짝짓지 않아도 되고, 누적 컬럼을 올리고 내리는 동기화가 없다
- 감수하는 것: `CANCEL_UNKNOWN`을 사람이 확정하기 전까지 그 결제의 추가 취소가 막힌다
- 감수하는 것: 확인 중 결제사가 거절한 취소는 실패가 아니라 `CANCEL_UNKNOWN`으로 끝나 사람이 확정한다
- 감수하는 것: 취소 금액 가드마다 취소 목록을 메모리에서 합산한다(취소 건수가 적어 충분)
