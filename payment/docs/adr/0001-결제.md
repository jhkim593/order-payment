# 0001. 결제: 명확한 답을 받았을 때만 확정하고, 모르면 확인을 거쳐 사람이 확정한다

## 2026-10-14 (적용 중)

### 배경

- 결제사 호출이 타임아웃·연결 끊김·5xx로 끝나면 결제 여부를 알 수 없다. 실패로 확정하면 돈은 빠졌는데 주문에는 실패가 통지된다
- 응답 뒤에 확정된 결과(확인, 수동 확정)는 전달할 길이 없다
- 확인 스케줄러가 여러 인스턴스에서 돌면 같은 행을 중복으로 묻고 확인 횟수를 빨리 소진한다
- 마지막 확인 직후 같은 흐름에서 `UNKNOWN`을 저장하면, 확인 횟수 선점은 이미 커밋돼 저장 실패 시 `PENDING`·4회로 남아 다시 잡히지 않는다

### 결정

1. **결제 건 생성**: 결제사 호출 전에 `PENDING` 결제를 먼저 커밋한다. 주문당 하나(`order_id` UNIQUE). `checked_at`은 요청 시각으로 채운다
2. **결제사 호출**: 결제사에는 한 번만 요청한다. HTTP 클라이언트는 JDK `HttpClient`. `HttpURLConnection`은 연결이 끊기면 POST를 몰래 재전송해, 재전송이 409를 받으면 돈이 나간 결제를 실패로 확정한다
3. **응답 판정**: 예외 종류가 아니라 답을 받았는지로 가른다. 판정은 결제사 호출 어댑터 한 곳에서 하고, `PG_PAYMENT_FAILED`(거절) / `PG_PAYMENT_UNKNOWN`(알 수 없음) 두 코드로 던진다
   - 200 → `SUCCEEDED`
   - 사전 검증 실패(호출 안 함)·4xx → `FAILED`. 명시적 거절이라 재시도해도 같다
   - 그 외 전부(연결 실패·타임아웃·5xx·응답 파싱 실패 등) → `PENDING` 유지. 예상 못 한 예외도 안전한 쪽으로 떨어진다
4. **확정 시 이벤트**: 성공·실패로 바뀌면 같은 트랜잭션에서 아웃박스로 결과 이벤트를 발행한다. 응답·확인·수동 확정 어느 경로든 같다
5. **요청 응답**: 성공 200, 거절 4xx, 결과를 모르면 `PENDING` 결제를 202. 503은 재시도를 부르지만 결제 건은 이미 만들어졌으므로 쓰지 않는다. 202는 결제 건이 커밋된 뒤에만 나가므로, 받는 쪽은 결과 이벤트를 기다리면 된다
6. **확인**: 80초 뒤 첫 확인, 이후 10초 간격, 최대 4번. 상태만 묻고 결제를 다시 요청하지 않는다. `PAID`·`FAILED` 답만 확정하고 그 외(NOT_FOUND 등)는 다음 확인을 기다린다
   - 분산 락 없이 `UPDATE ... RETURNING` + `FOR UPDATE SKIP LOCKED` 한 쿼리로 대상을 점유한다. 조회와 점유가 한 쿼리라 그사이 상태가 바뀌는 틈이 없다. 점유한 인스턴스가 죽어도 대기 시간이 지나면 다른 인스턴스가 회수한다
   - 첫 확인(`check_count` 0)과 재확인(1 ~ `CHECK_LIMIT - 1`)은 같은 쿼리를 조건만 바꿔 두 번 호출한다. 정책 값은 파라미터로 넘긴다
   - 기준 시각은 DB `now()`가 아니라 넘겨받은 `checkedAt`. `checked_at`과 같은 시계로 비교한다
7. **한도 소진**: 별도 스케줄러가 확인을 다 쓴 `PENDING`을 `UNKNOWN`으로 바꾸고 관리자에게 알린다. 결제사를 부르지 않는 멱등 작업이라 점유하지 않고, 실패해도 다음 사이클에 다시 잡힌다. `checked_at < now - 10초` 조건으로 진행 중인 마지막 확인 결과를 덮어쓰지 않는다
8. **수동 확정**: `UNKNOWN`은 자동 재시도하지 않고(이중 결제 위험) 이벤트도 보내지 않는다. 실패가 아니라 결과 미확정이라 받는 쪽이 할 일이 없다. 사람이 결제사에서 확인해 확정하면 4번의 결과 이벤트가 나간다. 수동 전이는 `confirm*` 접두사로 구분한다

```sql
UPDATE payment
   SET check_count = check_count + 1, checked_at = :checkedAt
 WHERE payment_id IN (
       SELECT payment_id FROM payment
        WHERE status = :status
          AND check_count BETWEEN :minCheckCount AND :maxCheckCount
          AND checked_at < :checkedAt - :intervalSeconds
        ORDER BY payment_id
        LIMIT :limit
        FOR UPDATE SKIP LOCKED)
RETURNING *
```

### 트레이드오프

- 얻는 것: 돈이 나간 결제를 실패로 통지하지 않고, 어디서 확정되든 결과가 유실 없이 전달된다. 미확정 건은 반드시 `UNKNOWN`으로 올라와 알림이 나간다. 확인 점유는 락 서버·락 테이블 없이 행 하나로 끝난다
- 감수하는 것: 결제사 장애로 요청이 도달하지 못한 결제도 `UNKNOWN`이 되어 사람이 확정해야 한다
- 감수하는 것: 같은 결과가 응답과 이벤트로 두 번 전달돼 받는 쪽이 중복을 걸러야 하고, 200과 202를 구분해야 한다
- 감수하는 것: 확인 쿼리만 네이티브 SQL이고 Postgres 문법에 묶인다
- 감수하는 것: `UNKNOWN` 전환이 최대 10초 늦고, 인스턴스가 겹치면 알림이 두 번 나갈 수 있다. 결제사 상태 조회 타임아웃은 10초 미만이어야 한다
- 감수하는 것: 수동 확정은 3시간 안에 해야 안전하다. 이후엔 결제사 멱등키가 만료돼 금액·시각으로 대조해야 한다
