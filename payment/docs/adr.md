## 0005. 취소는 별도 테이블로 분리한다

**상태:** 승인 · 2026-10-04

### 맥락

부분 취소를 도입하면 한 결제에 취소가 N건 생긴다. 지금은 `payment` 한 행이 취소 한 건을 겸하고 있어 1:N으로 늘어날 수 없다.

- `pg_cancellation_id`, `cancelled_at` — 단일 값 컬럼
- `status` — 결제 상태와 취소 상태가 한 컬럼에 섞여 있음
- `check_count`, `checked_at` — 취소를 시작할 때 리셋해 결제용과 취소용을 돌려씀

### 결정

`payment_cancellation` 테이블로 취소를 분리한다. 각 취소 건이 자기 금액·상태·확인 횟수를 갖는다.

`payment`에는 `cancelled_amount`(누적)가 들어가고 `pg_cancellation_id`, `cancelled_at`은 빠진다. 결제가 전부 취소됐는지는 `cancelled_amount == amount`로 판단한다.

### 이유

한 결제의 취소 2건이 서로 다른 상태로 진행되는 것이 정상인 구조가 되어야 한다. 한 행으로는 표현할 수 없다.

누적 컬럼을 두는 것은 초과 취소 가드(`cancelled_amount + 요청금액 <= amount`)를 매번 집계 없이 걸기 위해서다. 취소 요청 시 누적하고, 실패로 확정되면 되돌린다.

## 0004. 한 결제에 진행 중인 취소는 하나만 허용한다

**상태:** 승인 · 2026-10-04

### 맥락

부분 취소에서는 **결제사 응답이 유실됐을 때 어느 취소 건이 반영됐는지 알아낼 방법이 없다.**

결제는 우리가 `paymentId`를 지정해 보내므로 응답을 못 받아도 그 id로 조회하면 된다. 반면 취소는 결제사가 `cancellation.id`를 발급하고, 요청 본문에 우리 식별자를 넣을 필드가 없다. 응답을 못 받으면 그 id를 손에 넣지 못한다. 결제 조회의 취소 내역에서 금액으로 짝지으려 해도 같은 금액 취소가 2건이면 구분되지 않는다.

### 결정

한 결제에 대해 **미확정 취소가 동시에 하나만 존재하도록 제한한다.** `PENDING` 또는 `UNKNOWN`인 취소가 있으면 새 취소 요청을 거절한다.

그러면 폴링 시 미확정 건이 항상 하나뿐이므로, 결제사의 누적 취소 금액이 우리가 아는 금액에서 요청 금액만큼 늘었는지만 보면 확정할 수 있다.

```
우리가 아는 누적 취소 = 30,000, 요청 = 10,000
  결제사 누적 = 40,000 → 반영됨 → 성공 확정
  결제사 누적 = 30,000 → 미반영 → 계속 폴링
```

### 이유

식별자 매핑 문제를 푸는 대신 **문제가 생기지 않는 구조로 바꾼다.** 취소 내역 배열을 파싱하고 우리 건과 짝지을 필요가 없어진다.

안전성도 따라온다. 10,000원 취소가 미확정인 상태에서 또 10,000원 취소를 받으면, 첫 건이 사실 성공이었을 경우 초과 환불이 나간다. 이 제약이 그것을 구조적으로 막는다.

운영 비용은 작다. 취소는 보통 수초 안에 끝나 미확정 구간이 드물고, 묶음 취소를 쓰면 품목 여러 개가 한 건이 되어 제약에 걸릴 일이 더 줄어든다.

### 결과

- 같은 가드를 주문 쪽에도 둔다 (`order_cancellation`)
- 결제 조회 응답에서 **누적 취소 금액**을 받아야 한다. 현재 `PortOneGetPaymentResponseDto`는 `status`, `paidAt`, `pgTxId`만 매핑하고 있다
- `UNKNOWN`을 사람이 확정하기 전까지 그 결제의 추가 취소가 막힌다. 미확정 금액이 있으면 다음 취소의 가능 금액도 계산할 수 없으므로 의도된 동작이다

### 멱등키

매핑 수단으로는 필요 없어졌지만 **이중 환불 보험으로 유지한다.** 현재 `cancelPayment`에는 `Idempotency-Key` 헤더가 없다(`billingKeyPayment`에는 있다). 결제사의 멱등 보장 기간은 3시간이다.

## 0003. UNKNOWN은 자동 복구하지 않고 사람이 확정한다

**상태:** 승인 · 2026-10-04

### 맥락

결제사 응답을 끝내 확인하지 못하면 `UNKNOWN`으로 내려간다. 이 상태를 자동으로 재시도할지, 주문에 알릴지 정해야 했다.

### 결정

자동 재시도하지 않는다. 주문에도 이벤트를 보내지 않는다. 운영자에게 알리고, 사람이 결제사에서 확인한 뒤 수동으로 확정한다. 확정 시점에 기존 성공/실패 이벤트가 발행되어 주문이 평소 흐름으로 복귀한다.

### 이유

`UNKNOWN`은 "실패"가 아니라 **"결과 미확정"**이다. 재시도하면 이중 환불 위험이 있고, 주문에 보내려 해도 성공·실패 어느 쪽으로도 처리할 수 없어 받는 쪽이 할 일이 없다. 확정된 결론이 생긴 뒤에 통지하는 것이 맞다.

### 결과

`UNKNOWN`에서 나가는 전이를 열어야 한다. 현재 `succeeded()`는 `PENDING`만 허용해 `UNKNOWN`이 영구 정지 상태다. 자동 경로와 구분되도록 `confirm*` 접두사를 쓴다.

수동 확정은 **3시간 안에** 이뤄지는 것이 안전하다. 그 이후에는 결제사 멱등키가 만료되어, 응답을 한 번도 받지 못한 건을 금액과 시각으로 눈대중 매칭해야 한다.

## 0002. 결제사 호출 실패는 "명확한 답을 받았는가"로 가른다

**상태:** 승인 · 2026-10-04

### 맥락

결제사 호출이 실패했을 때 즉시 실패로 확정할지, 중간 상태로 남겨 폴링에 맡길지 판단 기준이 필요했다. 기존 코드는 `SocketTimeoutException` 하나만 골라내고 나머지를 전부 실패로 단정했다.

### 결정

| 상황 | 처리 |
|---|---|
| 사전 검증 실패 (호출 안 함) | 즉시 `FAILED` |
| 연결 실패 (`ConnectException` 등) | 즉시 `FAILED` |
| 4xx 전부 | 즉시 `FAILED` |
| 타임아웃 · 커넥션 리셋 · 5xx | `PENDING` 유지 → 폴링이 확정 |

### 이유

4xx는 결제사가 요청을 받고 명시적으로 거절한 것이라 재시도해도 결과가 같다. 반면 5xx와 커넥션 리셋은 **요청이 처리됐는지 알 수 없어** 실패로 단정하면 돈은 나갔는데 주문에 "실패"를 통지하는 불일치가 생긴다.

"이미 취소됨" 4xx를 성공으로 수렴시키는 특수 분기는 두지 않는다. 폴링이 재요청이 아니라 상태 조회만 하므로 같은 결제에 취소를 두 번 보내는 경로가 없고, 중복 이벤트는 상태 가드가 호출 전에 막는다.

### 폴링 중 NOT_FOUND

같은 응답이라도 결제와 취소에서 뜻이 다르다.

| 폴링 대상 | NOT_FOUND의 의미 | 처리 |
|---|---|---|
| 결제 | 결제가 생성되지 않음 | `FAILED` 확정 |
| 취소 | 이미 성공했던 결제가 사라짐 — 모순 | `UNKNOWN` + 즉시 운영 알림 |

취소 쪽은 재조회해도 계속 NOT_FOUND이므로 확인 한도를 기다리지 않고 바로 내린다.

## 0001. 복구 스케줄러 중복 실행은 분산 락 대신 조건부 UPDATE로 막는다

**상태:** 승인 · 2026-10-04

### 맥락

복구 스케줄러가 미확정 결제를 폴링하며 결제사에 상태를 되묻는다. 인스턴스가 여러 대면 전부 같은 행을 집어 중복으로 묻고 확인 횟수를 인스턴스 수만큼 빨리 소진한다.

### 결정

Redis·ShedLock 같은 분산 락을 도입하지 않는다. 후보를 조회한 뒤 행마다 조건부 UPDATE를 날리고, 변경 행 수가 1인 인스턴스만 처리한다.

```sql
UPDATE payment
   SET check_count = check_count + 1, checked_at = :now
 WHERE payment_id = :id AND status = :status AND <확인 시각 도래>
```

### 용어

폴링은 결제를 다시 거는 것이 아니라 **결제사에 상태를 묻는 것**이므로 `check`(확인)로 센다. 결제사에 요청을 보내는 것은 처음 한 번뿐이다.

| | `check_count` | 다음 확인까지 |
|---|---|---|
| 결제 요청 직후 | 0 | 80초 |
| 1~3번째 확인 후 | 1, 2, 3 | 10초 |
| 4번째 확인 후 | 4 | 중단 → `UNKNOWN` |

`CHECK_LIMIT`이 곧 확인 횟수와 같아 어긋나는 숫자가 없다.

`checked_at`은 생성 시 결제 요청 시각으로 채운다. "마지막으로 결제사와 주고받은 시각"으로 읽으면 자연스럽고 `NOT NULL`도 유지된다.

### 이유

락 서버나 락 테이블 없이 행 하나로 끝나고, 점유한 인스턴스가 죽어도 대기 시간이 지나면 다른 인스턴스가 자동으로 회수한다. 락은 TTL 만료까지 물려 있다.

`WHERE`의 `status`는 찾기 위한 조건이 아니라 **조회와 UPDATE 사이의 상태 변화를 막는 가드**다. 빠뜨리면 그사이 완료된 결제를 메모리의 낡은 상태로 덮어쓸 수 있다.

### 대안

`UPDATE ... RETURNING`으로 조회와 점유를 한 번에 처리하는 방식을 검토했고 Hibernate 7.2 + Postgres에서 동작하는 것도 확인했다. 쿼리 수가 줄고 `FOR UPDATE SKIP LOCKED`로 인스턴스 간 작업 분배까지 되지만, 코드베이스 전체가 QueryDSL인데 여기만 네이티브 SQL이 되는 비용이 더 크다고 판단했다. 폴링 백로그가 한 사이클에 다 돌지 못하는 것이 보이면 이 메서드만 교체한다.
